# Census / Benefits-Invoice Reconciler

Extracts per-employee benefit data from a Paychex PEO benefits invoice
(PDF) and demographic data from a raw census workbook (Excel), aligns the
two by employee name, fills the result into the **Prestige census
template**, and produces a reconciliation report of discrepancies.

This was built and validated against the four sample files actually
provided:

| File | Role |
|---|---|
| `Benefits_Invoice_-_May_2026.pdf` | Source of per-employee medical/dental/vision/life/LTD/STD plan enrollment + price |
| `Census.xlsx` | Source of employee/dependent demographics (name, DOB, zip, relationship, state, etc.) — plan/price columns are blank |
| `prestige_templet_-_Format.xlsx` | The target output layout (blank data rows, fixed header at row 24, data starting row 26) |
| `Worked_Census.xlsx` | A human-completed example of the target output — used here only as a sanity-check reference, not as a hidden input |

## Tech stack

- **Python 3.10+**
- **openpyxl** — reads/writes both the Census workbook and the Prestige
  template directly (needed because both have a multi-row letterhead
  above the real data table; `pandas.read_excel` would require awkward
  `skiprows` guessing, so we address known rows explicitly).
- **pandas** — available for any ad-hoc data-quality checks / CSV export
  work; the core pipeline uses openpyxl directly for row-precise control.
- **pdfplumber** — PDF text extraction. This is a plain-text (not
  scanned/image) invoice, so text extraction + regex is reliable and
  fully deterministic for the numbers that matter.
  > The task brief mentions PyMuPDF (`fitz`); this repo defaults to
  > `pdfplumber` because it was the available backend in the build/test
  > environment. `pdf_extractor.py`'s `_read_pages()` is the single swap
  > point — replace its body with `fitz.open(...)` page iteration to use
  > PyMuPDF instead; no other code changes are required.
- **No mandatory LLM/network dependency.** The "LLM-assisted" steps
  (fuzzy name matching, plan-name classification) ship with a solid
  rule-based baseline (`difflib` + keyword rules) so the whole pipeline
  runs offline and deterministically. Each of those functions documents
  exactly where to plug in a real LLM call for the residual ambiguous
  cases — see **LLM-assisted normalization**, below.

## How to run locally

```bash
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt

python src/main.py
```

That's it — with no arguments it uses the sample files already in
`input/` and writes to `output/`. To point it at different files:

```bash
python src/main.py \
  --pdf      path/to/invoice.pdf \
  --census   path/to/census.xlsx \
  --template path/to/prestige_template.xlsx \
  --output   path/to/filled_output.xlsx \
  --report-json path/to/report.json \
  --report-csv  path/to/report.csv
```

## Data model (Prestige template fields)

`src/config.py` is the single source of truth for column layout. The
template's data table starts at **row 26** (row 24 is the header, row 25
is blank), column **A**, one row per census person (employee or
dependent):

| Field | Column | Source |
|---|---|---|
| row_no | A | generated (1..N) |
| first_name / last_name | B / C | Census.xlsx |
| gender | D | Census.xlsx |
| dob | E | Census.xlsx |
| home_zip | F | Census.xlsx |
| relationship | G | Census.xlsx (`EE` = subscriber, else dependent) |
| dependent_of_employee_number | H | Census.xlsx |
| medical_coverage_tier | I | **PDF** (falls back to Census if PDF has no match) |
| cobra | J | Census.xlsx |
| medical_plan_enrolled / medical_plan_price | K / L | **PDF** |
| dental_coverage_tier / plan / price | M–O | **PDF**, falls back to Census |
| vision_coverage_tier / plan / price | P–R | **PDF**, falls back to Census |
| life_plan_name / benefit / rate | S–U | plan+rate from **PDF**; benefit ($ amount insured) from Census if present |
| ltd_plan / benefit / rate | V–X | plan+rate from **PDF** |
| std_plan / benefit / rate | Y–AA | plan+rate from **PDF** |
| work_state, job_title, workers_comp_code, annual_salary, ft_pt | AB–AF | Census.xlsx (not present on the PDF) |

## Extraction modules

### PDF (`pdf_extractor.py`)
- Reads every page's text via `pdfplumber` (backend-swappable, see above).
- Two regexes do all the work:
  - `EMPLOYEE_HEADER_RE` matches lines like `Abraham, Luis - 728` or
    `Candelora, Kari M - 1060 (Termination)`, starting a new employee
    block (or resuming one if it was already open, since employee blocks
    can be split across a page boundary in this invoice).
  - `PLAN_LINE_RE` matches a benefit line, e.g.
    `AET METRO NTL EPO 4000-80 EE MAY 2026 $ 618.80 $ 0.00 $ 618.80 $ 0.00`,
    capturing plan name, coverage tier, month, an optional
    `PREMIUM DUE`/`PREMIUM CREDIT` flag, and all four dollar columns.
- `extract_invoice_summary()` separately grabs the page-1 account summary
  (client number, statement date, grand total) for the report header.
- Lines matching neither pattern (wrapped headers, page footers) are
  silently skipped — by design, since the two regexes are specific enough
  that a near-miss usually means "not a data line" rather than "a data
  line I mis-parsed." If you need airtight coverage guarantees, add an
  `unparsed_line_count` counter (there's a comment marking exactly where).

### Excel (`census_extractor.py`)
- Opens the workbook with `openpyxl` (not `pandas.read_excel`) so the
  known header/data row offsets in `config.py` can be used directly,
  rather than relying on pandas to correctly infer a header row that
  sits under a multi-row letterhead.
- Walks rows starting at row 26 until two consecutive fully-blank rows
  are found (end-of-table sentinel).
- Every column is read verbatim into a `CensusRow` dataclass; `.is_dependent`
  is derived from the `relationship` column (`EE` = subscriber).

## LLM-assisted normalization & alignment strategy

Two genuinely ambiguous problems sit between the two deterministic
extractors:

1. **Name matching** — `"Acosta III, Joseph A"` (PDF) vs. `"Joseph" /
   "Acosta III"` (Census); order, middle initials, and suffixes differ
   between the two systems.
2. **Plan classification** — turning a raw string like
   `"AET METRO NTL EPO 4000-80"` into "this goes in the *medical*
   column" requires the kind of fuzzy, vocabulary-based judgment an LLM
   is well suited for.

`normalize.py` ships a **rule-based baseline** for both (`difflib`
sequence matching for names; keyword rules in `config.PLAN_CATEGORY_RULES`
for plans) so the pipeline runs fully offline, deterministically, and
without an API key. Both functions are written as clean, single-purpose
seams:

```python
# normalize.py
def best_fuzzy_match(target_key, candidate_keys, cutoff=0.82): ...
def classify_plan(plan_name): ...
def call_llm_for_ambiguous_matches(unmatched_pdf_names, unmatched_census_names, llm_client=None): ...
```

To upgrade to LLM-assisted matching for the residual cases the rules
can't confidently resolve (see `match_stats.unmatched_census_employees`
/ `unmatched_pdf_employees` in the report), implement
`call_llm_for_ambiguous_matches()`:

1. Batch the two unmatched-name lists into one prompt.
2. Ask the model to return strict JSON pairs, e.g.
   `[{"pdf_name": "...", "census_name": "...", "confidence": "high"}]`,
   explicitly allowing "no match" so it doesn't force bad pairings.
3. Only accept `confidence: high` pairs automatically; route anything
   else to a human review queue (the CSV report is designed to be that
   queue — open it, sort by `match_method`, review `fuzzy` and add any
   LLM-suggested pairs manually or via a follow-up script).

This keeps the *default* pipeline dependency-free and reproducible for
grading, while making the LLM upgrade a contained, ~20-line change.

## Validation / reconciliation rules implemented

- **Normalization**: money strings (`"$ 1,236.16"`) → floats; coverage
  tier strings uppercased/stripped; dates passed through as native
  `datetime` objects from openpyxl (Excel-native, no reformatting needed
  downstream).
- **Matching**: exact name match first, then fuzzy (`difflib`,
  cutoff 0.82) for the remainder; dependents inherit their subscriber's
  PDF match (the invoice is keyed by subscriber, not by dependent).
- **Discrepancy flags** (see `reconcile._flag_discrepancies`):
  - No PDF invoice match found for a census employee.
  - Match was fuzzy rather than exact (flagged for review even if the
    match itself is very likely correct).
  - Census's existing medical-tier value disagrees with the PDF-derived
    tier.
  - Census implies active medical coverage but no medical line was found
    on the invoice for that employee.
- **Known limitation (documented, not silently hidden)**: employees who
  share a first+last name after suffix-stripping (e.g. two people
  reducing to `"joseph acosta"` once `Jr`/`III` is stripped) can collide
  in the name index and match to the wrong PDF block. The sample data
  contains exactly this case (the "Acosta" family). Production-hardening
  this would mean matching on the PDF's numeric employee ID against a
  unique employee identifier in the census, if one exists in your source
  system — the current sample files don't expose a shared ID, only
  names, so name matching (with its stated limitation) is the working
  solution here.

## Outputs / artifacts

Running `python src/main.py` produces:

1. **`output/Prestige_Census_Filled.xlsx`** — a copy of the Prestige
   template with every census row (employee + dependents) populated in
   the correct columns.
2. **`output/reconciliation_report.json`** — full structured report:
   invoice summary, match statistics, and every record's discrepancies.
3. **`output/reconciliation_report.csv`** — flattened one-row-per-issue
   version of the same report, convenient for a spreadsheet review pass.

## Phased plan

**Phase 1 — MVP (this repo, as delivered)**
- Deterministic PDF + Excel extraction.
- Rule-based name matching + plan classification.
- Template filling + JSON/CSV reconciliation report.
- Smoke tests against the real sample files.

**Phase 2 — Enhancements**
- Wire `call_llm_for_ambiguous_matches()` to a real LLM for the residual
  unmatched names, with a human-in-the-loop review queue for
  low-confidence suggestions.
- Disambiguate same-name collisions using PDF employee ID <-> a stable
  census identifier, once/if the source system exposes one.
- Add a `--dry-run` diff mode that compares a freshly generated output
  against a previous run (or against `Worked_Census.xlsx`-style ground
  truth) and reports cell-level deltas, for regression testing across
  invoice periods.
- Multi-month support: currently assumes one invoice period per run;
  extend `EmployeeBenefits` to key plans by month for trend reporting.
